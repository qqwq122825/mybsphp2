# 软件用户状态显示修复（2026-09-23）

## 原因

充值卡删除采用作废标记：`cards.status=revoked` 并记录 `revoked_at`，历史和到期时间仍保留。独立的 `user_status` 可能仍为 `active`。旧软件用户列表只判断 `user_status=frozen`，其他状态全部显示“正常”；账号模式也遗漏了撤销、到期等标签。

代理联动已检查卡状态、用户状态与撤销时间，所以会正确返回 `revoked`。未来的到期时间并不覆盖撤销状态。

## 修复范围

- 软件用户列表、快捷查询复用只读状态组件，明确显示正常、冻结、撤销、到期等状态。
- 卡本身作废、用户撤销或撤销时间存在时均显示“已撤销”；撤销优先于到期。
- 仅冻结已使用的充值卡仍保持与冻结软件用户的区别。
- 账号模式同步修复；Vue 保留服务端标签，撤销使用红色提示。
- 不修改线上数据、卡号、原到期时间、登录或代理联动权限；不自动恢复历史撤销记录。平台无到期时间的用户仍按平台语义显示，代理独立保留其限时授权约束。

## 部署

发布 `app/Models/Card.php`、`app/Models/ApplicationAccount.php`，两个已修改管理模板及新增的 `resources/views/components/admin/software-user-status.blade.php`。
前端执行 `npm run build` 后发布完整 `public/build`，不要混用旧 manifest 与新资源。使用站点匹配的 PHP 执行 `artisan view:clear`，按现有部署方式刷新 PHP OPcache。

本次没有数据库迁移或数据修复脚本。现存撤销卡在刷新后台后显示真实状态；无需重建代理账号或更新 DFMProxy。

## 验证

单元测试覆盖三种撤销来源、冻结/到期优先级、永久用户与未知状态；集成测试复现“充值卡删除但 user_status 仍为 active”，核对用户列表、快捷查询和联动快照，并断言卡记录没有被读取操作修改。前端测试检查状态标签和颜色映射。

本地验收：独立 MySQL 测试库运行 210 项，208 通过、2 跳过；前端 33 项通过；生产资源构建、相关 PHP 格式/语法及 diff 检查通过。本地浏览器已核对正常、已冻结、已到期、已撤销标签。代码和资源已在本地更新，尚未部署线上。
